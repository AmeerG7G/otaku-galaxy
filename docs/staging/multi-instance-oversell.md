# التحقّق من منع البيع فوق المخزون عبر عدّة نسخ

## لماذا يوجد هذا الملف

اختبار العملية الواحدة (`backend/tests/oversell-guard.test.ts`) **لا يفرّق**
بين قفلٍ في PostgreSQL وقفلٍ في ذاكرة العملية. كلاهما ينجح فيه. الفرق يظهر
لحظةَ تشغيل نسخةٍ ثانية خلف موازِن حِمل: لكل عملية ذاكرتُها، فقفلُ إحداهما
لا تراه الأخرى، ويعود البيع فوق المخزون.

السكربت أدناه يأتي بالطلبات من **عمليتَي خادم مستقلّتين** لا تشتركان إلّا في
قاعدة البيانات — وهو الوضع الوحيد الذي يُثبت أن الحماية في PostgreSQL.

## التشغيل

```bash
cd backend
npx tsx scripts/oversell-multi-instance.ts
```

المتغيّرات:

| المتغيّر | الافتراضي | المعنى |
|---|---|---|
| `TARGET_DATABASE_URL` | `TEST_DATABASE_URL` | القاعدة المشتركة بين النسختين |
| `PORT_A` / `PORT_B` | `4101` / `4102` | منفذا النسختين |
| `ROUNDS` | `10` | جولات الطلبين المتزامنين |
| `CONTENTION` | `6` | طلبات جولة الضغط، موزَّعة على النسختين |

مقابل بيئة staging حقيقية:

```bash
cd backend
TARGET_DATABASE_URL='postgres://…@staging-db:5432/otaku_galaxy_staging' \
  ROUNDS=20 CONTENTION=10 npx tsx scripts/oversell-multi-instance.ts
```

> لا يحتاج Docker ولا Kubernetes — عمليتان عاديتان و`PostgreSQL` واحدة.

## ماذا يفعل بالضبط

1. يرفض العمل إن كان أحد المنفذين مشغولاً (وإلّا قِيس خادمٌ قديم).
2. يشغّل نسختين مستقلّتين، ويتحقّق عبر `pg_stat_activity` أن لكلٍّ منهما
   مجمّع اتصالات خاصّاً (`application_name = oversell-instance-<port>`).
3. لكل جولة: منتجٌ جديد بمخزون 3، وزبونان يُسجَّلان **عبر نسختين مختلفتين**
   فتُنشأ عربتاهما في عمليتين مختلفتين، وكلٌّ يطلب 3 قطع **ويرسل طلبه** —
   كلا الإرسالين `201` والمخزون ما زال 3 (لا حجز عند الإرسال).
4. يُطلق **قبولَي** الطلبين — من مسؤولٍ بتوكنٍ من كل نسخة — عند طابعٍ
   زمنيّ واحد ليتداخلا قدر المستطاع.
5. يتحقّق من: `200` واحد، `409 INSUFFICIENT_STOCK` واحد، مبيع = 3،
   مخزون = 0، لا مخزون سالب، لا سطرَ طلبٍ يتيم، والخاسر باقٍ في
   `PENDING_ADMIN_CONFIRMATION` لا مقبولاً بلا بضاعة.
6. جولة ضغط: `CONTENTION` طلباً منتظراً بقطعةٍ واحدة، قبولاتها موزَّعة على
   النسختين — ينجح 3 بالضبط.
7. ينظّف ما زرعه ويقتل مجموعة العمليات كاملةً.

## ما الذي يحميها فعلاً

**[CONTRACT 2026-09-14]** المخزون يُستهلك عند **قبول الإدارة**
(`PENDING_ADMIN_CONFIRMATION → OUT_FOR_DELIVERY`) لا عند الإرسال. الإرسال
بوّابةُ طلبٍ فقط (`orderService.create`: تحقّقٌ من المجموع بلا قفل ولا كتابة).

| الموضع | الحارس |
|---|---|
| `applyStatusTransition` | `SELECT … FOR UPDATE` على صفّ الطلب ثم قراءة حالته تحت القفل — قبولان للطلب نفسه: الثاني «حالةٌ نفسها» بلا أثر |
| `consumeStockOnApproval` | `SELECT … ORDER BY id FOR UPDATE` على صفوف المنتجات، مرتّباً بالمعرّف لمنع الجمود |
| `consumeStockOnApproval` | تحقّقٌ من مجموع الكمية المطلوبة من كل منتج (لا سطراً سطراً) على المخزون **الحالي** |
| `consumeStockOnApproval` | `UPDATE … WHERE stock >= $2` مع فحص `rowCount` — فشلُه يُسقط المعاملة |
| `products.stock CHECK (stock >= 0)` | حارس القاعدة الأخير ضد السالب |

المعاملة واحدة: إن فشل أيُّ حارس، تُلغى كلها — لا تنزيلَ جزئياً ولا طلبَ
مقبولاً بلا بضاعة؛ يبقى منتظراً ويعود `409 INSUFFICIENT_STOCK`.

**لا يوجد مسار بديل**: `PATCH /api/admin/orders/:id/status` هو المدخل
الوحيد للقبول، والمخزون يُنقَص في موضعٍ واحد (`consumeStockOnApproval`)
ويُعاد في موضعٍ واحد (`releaseStockOnRejection`: رفضُ طلبٍ سبق قبوله).

## ما يبقى معلَّقاً

هذا تحقّقٌ محلّي بعمليتين على جهاز واحد. **التحقّق على staging المنشور
فعلياً — خلف موازِن حِمل حقيقي وبقاعدة staging — لم يُنفَّذ بعد**، لأن تلك
البيئة غير متاحة من هنا. السكربت جاهز لها بمتغيّر `TARGET_DATABASE_URL`.

الفرق الذي يبقى غير مُقاس: زمن الشبكة بين الموازِن والنسخ، وسلوك المجمّع
تحت ضغطٍ حقيقي. أمّا دلالة القفل نفسها فهي دلالةُ PostgreSQL ولا تتغيّر
بتغيّر المضيف.

## متابعات مسجَّلة (لم تُعالَج هنا)

**تكرار منتجات في قاعدة التطوير.** كان الزرع يُدرج نسخةً جديدة في كل تشغيل
لأن `ON CONFLICT DO NOTHING` بلا قيدٍ فريد لا يفعل شيئاً — أُصلح السبب،
لكن الصفوف المكرّرة السابقة باقية:

```sql
WITH d AS (
  SELECT id, name, row_number() OVER (
           PARTITION BY name, category_id, COALESCE(subcategory_id::text,'-')
           ORDER BY created_at, id) AS rn
    FROM products)
SELECT count(*) FILTER (WHERE rn>1) AS dupes,
       count(*) FILTER (WHERE rn>1 AND EXISTS (
         SELECT 1 FROM order_items oi WHERE oi.product_id=d.id)) AS with_orders
  FROM d;
```

آخر قياس: **11 صفّاً مكرّراً، خمسة منها مرتبطة بطلبات حقيقية**. حذفُ
الخمسة يكسر تاريخ الطلبات، فالتنظيف قرارُ بيانات لا قرارُ شيفرة ولم
يُتَّخذ هنا.
