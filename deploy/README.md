# نشر مجرّة الأوتاكو — دليل التشغيل

هذا المجلد يحوي **كل** ما يمكن تحضيره قبل وجود خادم حقيقي. ما تبقّى بعده
مذكور في آخر الملف تحت «ما يحتاج خادماً».

> **لم يُنشر شيء.** الملفات هنا إعداد مُراجَع لا نشرٌ منفَّذ. النطاقات قيم
> نائبة (`api.example.com`)، ولا سرّ واحد في هذا المستودع.

> **[حرِج] R-17 — عزل البيئتين على خادمٍ واحد (2026-10-24).** كانت أوامر §٢–§٥
> تبني الاختبار المسبق في مجلّد الإنتاج نفسه (PM2)، وتشغّل البيئتين بمشروع compose
> واحد ووسم صورة واحد وحجم صورٍ واحد (Docker)، وتفعّل موقع nginx قبل وجود شهادته،
> وكان الموقع يرجع إلى API الإنتاج (`127.0.0.1:4000`) إن غاب `API_INTERNAL_URL`.
> صُحِّحت كلها هنا وفي الملفات (`docker-compose.yml`، `deploy/pm2`، `web-store`)،
> وتحرسها `backend/tests/deploy-runbook.test.ts`. القواعد:
>
> | | الاختبار المسبق | الإنتاج |
> |---|---|---|
> | نسخة المستودع | `/srv/otaku-galaxy-staging` | `/srv/otaku-galaxy` |
> | مشروع compose | `-p otaku-staging` | `-p otaku-prod` |
> | منفذ API / الموقع | `4001` / `3001` | `4000` / `3000` |
> | وسم الصورة | `staging-<commit>` | `prod-<commit>` |
>
> **كل كتلة أوامر قشرةٌ فرعية** `( set -e … )` تبدأ بـ`cd` إلى نسخة بيئتها وفحص فرعها:
> `cd` فاشل أو فرعٌ خاطئ يوقف الكتلة قبل أي بناء، ولا يبقى `export` بعدها ليصيب كتلة
> البيئة الأخرى. لا تُلصق الأوامر سطراً سطراً في قشرتك.
>
> **لا تُشغَّل على خادمٍ يستضيف بيئةً قائمة** قبل §٠ أدناه: الأوامر لم تُنفَّذ على
> خادمٍ حقيقي، ونقلُ بيئةٍ قائمة إلى اسم مشروعٍ أو مجلّدٍ آخر يُنشئ حجم صورٍ فارغاً
> بجانب القديم. §١٣ (الموقع) **لا تُشغَّل** كلها حتى تُراجَع على خادم.

### ٠. قبل أول أمرٍ من هذا الدليل على خادمٍ قائم — للقراءة فقط

```bash
docker compose ls                                   # أسماء المشاريع القائمة
docker ps --format '{{.Names}}\t{{.Image}}\t{{.Ports}}'
docker volume ls | grep -i uploads
pm2 ls 2>/dev/null
for app in otaku-api-staging otaku-api-prod otaku-web-staging otaku-web-prod; do
  pm2 describe "$app" 2>/dev/null | grep -E 'exec cwd|script path' | sed "s/^/$app /"
done
ls -d /srv/otaku-galaxy* 2>/dev/null
nginx -v; sudo nginx -t; ls -l /etc/nginx/sites-enabled/
```

إن كانت بيئةٌ تعمل باسم مشروعٍ أو مجلّدٍ غير ما في الجدول أعلاه: **توقّف**. نقلُها
قرارٌ للمشغّل مع نسخةٍ احتياطية من حجم الصور، لا خطوةٌ ضمن هذا الدليل. الاستثناء
الوحيد: `otaku-api-staging` في `/srv/otaku-galaxy/backend` (التخطيط القديم) — §٣ يحذفه
ويعيد إنشاءه في مجلّده، لأن إعادة تشغيل تطبيق PM2 تُبقي مجلّده القديم.

`sudo nginx -t` يجب أن ينجح قبل أي شيء، وملفّا `deploy/nginx` يستعملان `http2 on;`
الذي يحتاج nginx **1.25.1 أو أحدث** (أوبونتو 24.04 يأتي بـ1.24): على أقدم منه يفشل
`nginx -t` في §٤ فيتراجع الأمر عن التفعيل — ارفع nginx أولاً.

## ٢. المسار الأول: Docker

**[حرِج] كل بيئة من نسختها وباسم مشروعها.** compose يسمّي المشروع باسم المجلّد
إن لم يُعطَ `-p`، والحاوية والحجم يتبعان المشروع: من مجلّدٍ واحد يستبدل `up`
الإنتاج حاويةَ الاختبار المسبق والعكس، ويكتبان الصور في حجمٍ واحد. والوسم
`otaku-galaxy-api:<tag>` عامٌّ على الخادم كله، فوسمٌ مشترك يعني أن بناء الاختبار
المسبق يصير صورة الإنتاج عند أول إعادة إنشاء. لذلك لا قيمة افتراضية في
`docker-compose.yml` لأيٍّ من `ENV_FILE` و`HOST_PORT` و`IMAGE_TAG`: غيابها يوقف
compose برسالة. وهي مطلوبة حتى لأمر `migrate`، لأن compose يفسّر الملف كله.

```bash
# مرةً واحدة: نسخة الاختبار المسبق على فرع staging
sudo install -d -o "$USER" -g "$USER" /srv/otaku-galaxy-staging
git clone --branch staging https://github.com/AmeerG7G/otaku-galaxy.git /srv/otaku-galaxy-staging

# كل إصدار
( set -e
  cd /srv/otaku-galaxy-staging
  test "$(git rev-parse --abbrev-ref HEAD)" = staging
  export ENV_FILE=./backend/.env.staging HOST_PORT=4001 IMAGE_TAG=staging-$(git rev-parse --short HEAD)
  # الصورتان معاً: `run` لا يبني `migrate` إن وُجدت صورتها، فتبقى هجرات الإصدار السابق
  docker compose -p otaku-staging build api migrate
  docker compose -p otaku-staging --profile tools run --rm migrate
  docker compose -p otaku-staging up -d api
  docker compose -p otaku-staging ps          # يجب أن تكون الحالة healthy
  curl -fsS localhost:4001/health
)
```

للإنتاج — من نسخة الإنتاج وحدها، بعد أن مرّ الإصدار نفسه على الاختبار المسبق:

```bash
( set -e
  cd /srv/otaku-galaxy
  test "$(git rev-parse --abbrev-ref HEAD)" = prod
  export ENV_FILE=./backend/.env.prod HOST_PORT=4000 IMAGE_TAG=prod-$(git rev-parse --short HEAD)
  docker compose -p otaku-prod build api migrate
  docker compose -p otaku-prod --profile tools run --rm migrate
  docker compose -p otaku-prod up -d api
  docker compose -p otaku-prod ps
  curl -fsS localhost:4000/health
)
```

### المنفذان: الداخلي والخارجي

| | بلا حاويات (PM2) | بحاويات (Docker) |
|---|---|---|
| ما يستمع عليه التطبيق | `PORT` من ملف البيئة (4001 اختبار / 4000 إنتاج) | **4000 دائماً** — يفرضه compose |
| ما يقصده nginx | `PORT` نفسه | `HOST_PORT` (4001 / 4000) |
| عنوان الاستماع | `127.0.0.1` افتراضياً (`HOST`) | `0.0.0.0` داخل الحاوية — يثبّته `docker-compose.yml` فوق ملف البيئة، والمنفذ يُنشر على `127.0.0.1` للمضيف |

**[حرِج]** الحاوية معزولة شبكياً فلا معنى لتمييز منفذها الداخلي؛ التمييز
يقع على منفذ المضيف. لذلك يفرض compose `PORT=4000` داخل الحاوية ويطغى على
ملف البيئة. لولا ذلك لاستمع الاختبار المسبق على 4001 بينما يوجّه compose
إلى 4000 — خدمةٌ غير قابلة للوصول و«غير صحّية» دائماً بلا رسالة خطأ.

**لماذا الهجرة خدمة منفصلة:** `scripts/migrate.ts` خارج `rootDir` في
`tsconfig.json` فلا يترجمه `tsc`، ويحتاج `tsx` وهي أداة تطوير لا مكان لها في
صورة الإنتاج. فتعمل الهجرة من مرحلة `builder` وتبقى صورة التشغيل نظيفة من
اعتماديات التطوير. وهي خطوة يقرّرها المشغّل عمداً: الهجرة التلقائية عند كل
إقلاع تعني أن كل نسخة تحاول الهجرة معاً، وأن فشلها يمنع الخدمة كلها.

## ٣. المسار الثاني: PM2

**[حرِج] كل بيئة في مجلّدها** (`cwd` في `deploy/pm2/ecosystem.config.cjs`):
`/srv/otaku-galaxy-staging/backend` للاختبار المسبق و`/srv/otaku-galaxy/backend`
للإنتاج. كانتا مجلّداً واحداً: `npm run build` للاختبار المسبق كان يستبدل `dist/`
الذي يشغّله الإنتاج عند أول إعادة تشغيل (عطل، سقف ذاكرة، إقلاع الخادم)، و`uploads/`
(نسبيٌّ إلى المجلّد) كان واحداً للبيئتين.

```bash
# مرةً واحدة: النسخة (§٢)، ومجلّد سجلّات يملكه مستخدم PM2 — `mkdir` بـsudo يتركه
# لـroot فيفشل فتح السجلّات ويبقى التطبيق `errored`.
sudo install -d -o "$USER" -g "$USER" /var/log/otaku-galaxy

( set -e
  cd /srv/otaku-galaxy-staging
  test "$(git rev-parse --abbrev-ref HEAD)" = staging
  cd backend
  npm ci && npm run build
  # بيئةٌ نظيفة (`env -i`): dotenv لا يطغى على متغيّرٍ موجود، وPM2 يدمج متغيّرات
  # القشرة في التطبيق — `DATABASE_URL` مُصدَّرٌ في قشرتك كان سيصير قاعدة الاختبار المسبق.
  env -i HOME="$HOME" PATH="$PATH" npm run db:migrate:staging
  cd ..                                     # ملف PM2 في جذر المستودع لا في backend/
  # تطبيقٌ بالاسم نفسه من التخطيط القديم يُبقي مجلّده عند إعادة التشغيل: يُحذف أولاً.
  if pm2 describe otaku-api-staging >/dev/null 2>&1 &&
     ! pm2 describe otaku-api-staging | grep -q 'exec cwd.*/srv/otaku-galaxy-staging/backend'; then
    pm2 delete otaku-api-staging
  fi
  env -i HOME="$HOME" PATH="$PATH" pm2 start deploy/pm2/ecosystem.config.cjs --only otaku-api-staging
  pm2 save
  curl -fsS localhost:4001/health
)
pm2 startup     # مرةً واحدة: يطبع أمر sudo — شغّله، وإلا لا ينجو PM2 من إعادة الإقلاع
```

للإنتاج الكتلة نفسها من `/srv/otaku-galaxy` بفرع `prod` و`db:migrate:prod` و`--only
otaku-api-prod` و`localhost:4000` — بلا خطوة الحذف (مجلّد الإنتاج لم يتغيّر). لا يُبنى في
مجلّد الإنتاج إلا إصدار الإنتاج.

الأسرار ليست في ملف PM2. التطبيق يقرأ `.env.${APP_ENV}` من مجلّد التشغيل
عبر dotenv، فيكفي أن يحدّد PM2 البيئة ويترك القيم لملفٍ يعيش على الخادم
وحده.

**نسخة واحدة لا عنقود.** الجدولة نفسها آمنة تحت أكثر من نسخة
(`FOR UPDATE SKIP LOCKED` في `ratingReminderJob`)، لكن حدود المعدّل في
`express-rate-limit` تعيش في ذاكرة العملية: أربع نسخ تعني أربعة دلاء
مستقلة، أي أربعة أضعاف السقف الفعلي لتخمين كلمات المرور ورموز التحقق. رفعُ
عدد النسخ يتطلّب مخزناً مشتركاً للحدود (Redis) **أولاً**.

## ٤. الوسيط العكسي

**[حرِج] الشهادة قبل الموقع (§٥).** ملفّا nginx يشيران إلى
`/etc/letsencrypt/live/<النطاق>/`؛ تفعيلُ الموقع قبل وجودها يُفشل `nginx -t`، وكان
الرابط يبقى في `sites-enabled` بعد الفشل، فيرفض nginx الإقلاع عند أول إعادة تشغيل
أو إقلاعٍ للخادم — **ومعه الإنتاج** الذي يخدمه nginx نفسه. الأمر الآن لا يفعّل
بلا شهادة، ويُرجع ما كان إن فشل الفحص: الملف السابق يعود، والرابط يُزال فقط إن
أنشأه هذا التشغيل (تحديثُ موقعٍ مفعَّل لا يُطفئه). يُشغَّل من نسخة البيئة نفسها، فملف
الإنتاج من `/srv/otaku-galaxy` لا من نسخة الاختبار المسبق. يحتاج nginx 1.25.1 أو أحدث
(`http2 on;` — انظر §٠):

```bash
( set -e
  cd /srv/otaku-galaxy-staging                  # الإنتاج: /srv/otaku-galaxy وفرع prod
  test "$(git rev-parse --abbrev-ref HEAD)" = staging
  DOMAIN=staging-api.example.com CONF=staging-api.conf   # الإنتاج: api.example.com / api.conf
  AV=/etc/nginx/sites-available/$CONF EN=/etc/nginx/sites-enabled/$CONF
  if ! sudo test -s /etc/letsencrypt/live/$DOMAIN/fullchain.pem; then
    echo "لا شهادة لـ$DOMAIN — نفّذ §٥ أولاً"; false
  fi
  if sudo test -e "$AV"; then sudo cp -p "$AV" "$AV.bak"; fi
  sudo cp deploy/nginx/$CONF "$AV"
  CREATED=0
  if ! sudo test -e "$EN"; then sudo ln -s "$AV" "$EN"; CREATED=1; fi
  if sudo nginx -t; then
    sudo systemctl reload nginx
  else
    if [ "$CREATED" = 1 ]; then sudo rm "$EN"; fi
    if sudo test -e "$AV.bak"; then sudo mv "$AV.bak" "$AV"; else sudo rm "$AV"; fi
    echo "nginx -t فشل — أُعيد الإعداد السابق كما كان"; false
  fi
)
```

**[حرِج] `TRUST_PROXY` والوسيط يعملان معاً أو لا يعمل أيٌّ منهما.** الخادم
يقرأ `X-Forwarded-For` ليعرف عنوان الزبون. إن لم يمرّره nginx (أو إن لم
يُضبط `TRUST_PROXY`) رأى الخادمُ كلَّ الطلبات قادمةً من `127.0.0.1`، فانهار
حدّ المعدّل إلى دلو واحد مشترك بين كل المستخدمين وأُقفل التسجيل والدخول على
الجميع بعد أول عشرة طلبات. العطل يبدو خللاً في الشيفرة وهو إعداد.

المنافذ: الاختبار المسبق `4001`، الإنتاج `4000` — كي تتعايشا على خادم واحد
إن لزم.

## ٥. HTTPS / TLS

**لم تُصدَر أي شهادة، ولم تُنشأ شهادات وهمية.** الآلية الموصى بها:

`certbot --nginx` يحتاج إعداد nginx سليماً ويعيد كتابة ملفّات الموقع المراجَعة،
فالشهادة تُصدَر بـ`certonly --webroot` من موقع HTTP مؤقّت **لنطاقٍ جديد** لا يخدم
إلا التحدّي (نطاقٌ مفعَّل أصلاً يخدم التحدّي من ملفّه، فلا يحتاج المؤقّت):

```bash
sudo apt install certbot
sudo mkdir -p /var/www/certbot

( DOMAIN=staging-api.example.com
  sudo tee /etc/nginx/sites-available/acme-$DOMAIN.conf >/dev/null <<NGINX
server {
    listen 80;
    listen [::]:80;
    server_name $DOMAIN;
    location /.well-known/acme-challenge/ { root /var/www/certbot; }
    location / { return 404; }
}
NGINX
  sudo ln -s /etc/nginx/sites-available/acme-$DOMAIN.conf /etc/nginx/sites-enabled/
  if sudo nginx -t; then
    sudo systemctl reload nginx
    sudo certbot certonly --webroot -w /var/www/certbot -d $DOMAIN \
      --deploy-hook 'systemctl reload nginx'
  fi
  sudo rm /etc/nginx/sites-enabled/acme-$DOMAIN.conf && sudo nginx -t && sudo systemctl reload nginx
)
```

ثم §٤ للنطاق نفسه.

التجديد تلقائي عبر مؤقّت systemd الذي تثبّته certbot. تحقّق منه بـ:

```bash
sudo certbot renew --dry-run
systemctl list-timers | grep certbot
```

ملفّا nginx يُبقيان `/.well-known/acme-challenge/` على HTTP عمداً — تحويلُه
إلى HTTPS يكسر التجديد بصمت بعد تسعين يوماً، وهو عطلٌ يظهر متأخراً جداً.

**[حرِج] HSTS.** ملف الإنتاج يعلن `max-age=31536000; includeSubDomains`. لا
تُفعّله إلا بعد أن يعمل HTTPS على النطاق **وكل** نطاقاته الفرعية: المتصفح
يتذكّر التعليمة سنةً ويرفض بعدها أي اتصال غير مشفَّر، ولا سبيل للتراجع من
طرف الخادم. الاختبار المسبق يعلن يوماً واحداً عمداً لهذا السبب.

## ٦. بنية النطاقات

```
STAGING     staging-api.<domain>     ←  API الاختبار المسبق
            staging-admin.<domain>   ←  لوحة التحكم (CORS_ORIGINS)

PRODUCTION  api.<domain>             ←  API الإنتاج
            admin.<domain>           ←  لوحة التحكم (CORS_ORIGINS)
```

لا شيء في الشيفرة يعتمد على نطاق بعينه:

| الطرف | مصدر العنوان |
|---|---|
| الخادم | `PUBLIC_BASE_URL` من البيئة |
| لوحة التحكم | `vite build --mode staging\|prod` |
| فلاتر | `--dart-define=API_BASE_URL=https://…/api` |

## ٧. عقد المتغيّرات

القوالب الكاملة: `backend/.env.staging.example` و`backend/.env.prod.example`.
انسخ القالب إلى `.env.staging` / `.env.prod` **على الخادم** واملأه هناك.
`.gitignore` يمنع دخول الملفات الحقيقية إلى Git.

### ما يجب أن يقدّمه المشغّل — لا قيمة افتراضية له

| المتغيّر | ملاحظة |
|---|---|
| `APP_ENV` | `staging` أو `prod`. **مطلوب صراحةً**: غيابه مع `NODE_ENV=production` يمنع الإقلاع |
| `JWT_SECRET` | `openssl rand -hex 32`. **فريد لكل بيئة** |
| `DATABASE_URL` | قاعدة منفصلة تماماً لكل بيئة |
| `PUBLIC_BASE_URL` | مطلوب — بديله `localhost` يكسر كل رابط صورة على الهواتف |
| `TRUST_PROXY` | مطلوب — عدد الوسطاء (`1` خلف nginx واحد) |
| `CORS_ORIGINS` | أصل لوحة التحكم. فارغُه يمنع كل أصل (فشلٌ في الاتجاه الآمن) |
| `HOST` | اختياري. الافتراض خارج التطوير `127.0.0.1` — nginx على المضيف نفسه. لا تضبطه `0.0.0.0` بلا جدار ناري |
| `BFF_SHARED_SECRET` | اختياري حتى يُنشر الموقع (`web-store/`)، ثم مطلوب فيه وفي الخادم بالقيمة نفسها: `openssl rand -hex 32`. به يوقّع خادم الموقع عنوان الزبون، فتبقى حدود المعدّل لكل زبون لا دلواً واحداً لكل زوّار الموقع. **فريد لكل بيئة**. الخادم يحذّر في السجلّ (`[client-ip]`) إن وصلته ترويسة موقَّعة وهو بلا سرّ أو بسرّ مختلف. الطريق بين الموقع والخادم (`API_INTERNAL_URL`) محلي أو عبر TLS: التوقيع لا يحمي من يرى ذلك الطريق |
| `SEED_ADMIN_PHONE` · `SEED_ADMIN_PASSWORD` | مرة واحدة لإنشاء أول مسؤول، ثم يُزالان |

**لا يُعاد استعمال أي منها بين البيئات**: لا مفتاح توقيع، ولا وصلة قاعدة،
ولا اعتماد رسائل، ولا اعتماد تخزين.

## ٨. ما تحرسه الشيفرة عند الإقلاع

الخادم يرفض العمل — لا يحذّر ويكمل — في هذه الحالات:

- `APP_ENV` غير معروف أو غائب مع `NODE_ENV=production`
- `JWT_SECRET` مفقود أو معروف أو أقصر من ٣٢ حرفاً
- `DATABASE_URL` مفقود أو غير صالح
- `TRUST_PROXY` أو `PUBLIC_BASE_URL` مفقود خارج التطوير
- `HOST` ليس عنوان IP صالحاً
- `BFF_SHARED_SECRET` مضبوط وأقصر من ٣٢ حرفاً
- تعذّر الربط على `HOST:PORT` (منفذ مشغول، عنوان غير موجود على الجهاز): يخرج بالرمز 1 بلا سطر «running»

> **لا مزوّد رسائل ولا رمز تحقق.** إنشاء الحساب ونسيان كلمة المرور طلبان
> تحسمهما الإدارة من اللوحة بعد تحقّق واتساب يدوي؛ لا `SMS_*` ولا
> `DEV_OTP_*` تُضبط ولا تُفحص عند الإقلاع. (الشيفرة القديمة في `legacy/otp/`.)

بناء ما يُبنى يجري **عند الإقلاع** لا عند أول استعمال، فينكشف نقص الإعداد وقت
النشر لا عند أول زبون يحاول التسجيل.

## ٩. الصحّة والإغلاق

`GET /health` → `{"success":true,"data":{"status":"ok"}}`. لا يكشف إصداراً
ولا حالة قاعدة ولا أي تفصيل داخلي، ويستعمله فحص Docker وnginx معاً.

الإغلاق المنظَّم مُختبَر في الشيفرة: عند `SIGTERM`/`SIGINT` تتوقّف الجدولة،
ويُغلق خادم HTTP، ويُغلق مجمّع القاعدة، ثم تخرج العملية — بمهلة قسرية عشر
ثوانٍ حتى لا يعلق النشر على اتصال لا يُغلق. `stop_grace_period: 15s` في
compose و`kill_timeout: 15000` في PM2 أطول من ذلك عمداً.

`uncaughtException` و`unhandledRejection` يُنهيان العملية برمز خروج غير
صفري بعد إغلاق منظَّم. المواصلة بعد عطل غير قابل للتعافي أخطر من التوقّف:
قد تكون معاملةٌ نصفَ منفَّذة أو قفلٌ لم يُحرَّر، وخادمٌ يردّ ببيانات فاسدة
أسوأ من خادمٍ لا يردّ لأن الأول لا يُلاحَظ. المدير يعيد التشغيل على حالة
نظيفة.

## ١٣. STEP 68 — الموقع (`web-store/`) على الاختبار المسبق — **لا تُشغَّل**

> **[حرِج] لا تُشغَّل هذا القسم.** صُحِّح من مراجعة R-17 لكنه لم يُنفَّذ على خادم،
> ولم يُراجَع بعدُ على الخادم الحقيقي، وملف nginx للموقع **غير موجود** في
> `deploy/nginx/`. يُرفع هذا التحذير بعد: (١) §٠ على الخادم، (٢) كتابة ملف nginx
> للموقع ومراجعته، (٣) تنفيذٍ كامل على الاختبار المسبق تُسجَّل مخرجاته.

**ما تغيّر عن النسخة السابقة من هذا القسم (المفقودة مع حاوية الجلسة السحابية):**
البناء في نسخة الاختبار المسبق لا في مجلّد الإنتاج؛ PM2 يشغّل ملف Next التنفيذي
نفسه (`otaku-web-staging`) لا أمراً لا يبدأ Next؛ المنفذ 3001 لا 3000؛
`API_INTERNAL_URL` إلزامي في الإنتاج (كان غيابه يعني API الإنتاج على 4000)؛ nginx
بعد الشهادة لا قبلها.

**قبله:** API الاختبار المسبق يعمل على 4001 (§٢ أو §٣) والهجرة **083**
(`083_order_idempotency.sql`، إضافية) مطبَّقة، و`BFF_SHARED_SECRET` مضبوط في
`backend/.env.staging`.

```bash
# مرةً واحدة — الإعدادات على الخادم وحده، لا تدخل Git (web-store/.gitignore).
# لا تُنشأ فوق ملفٍ موجود: `install /dev/null` يفرّغه.
F=/srv/otaku-galaxy-staging/web-store/.env.production.local
[ -e "$F" ] || install -m 600 /dev/null "$F"
$EDITOR "$F"
#   API_INTERNAL_URL=http://127.0.0.1:4001/api       ← API الاختبار المسبق لا 4000
#   MEDIA_ORIGIN=https://staging-api.example.com
#   SITE_ORIGIN=https://staging.example.com
#   SESSION_SEAL_KEYS=<مفتاحٌ للاختبار المسبق وحده>
#   BFF_SHARED_SECRET=<القيمة نفسها في backend/.env.staging>

# كل إصدار
( set -e
  cd /srv/otaku-galaxy-staging
  test "$(git rev-parse --abbrev-ref HEAD)" = staging
  cd web-store
  npm ci && npm run build
  cd ..
  # `env -i`: Next لا يطغى على متغيّرٍ موجود من `.env.production.local`، وPM2 يدمج
  # القشرة — `API_INTERNAL_URL` أو `PORT` مُصدَّران هنا كانا سيغلبان ملف البيئة.
  env -i HOME="$HOME" PATH="$PATH" pm2 start deploy/pm2/ecosystem.config.cjs --only otaku-web-staging
  pm2 save
)
```

**التحقّق — كلّه يجب أن ينجح قبل nginx:**

```bash
ss -ltnp | grep ':3001 '                             # node على 127.0.0.1:3001 وحده
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3001/     # 200 — الصفحة تقرأ الـAPI
pm2 logs otaku-web-staging --lines 30 --nostream     # لا «API_INTERNAL_URL is required»
```

ثم منتجٌ تجريبي تنشئه لوحة الاختبار المسبق يظهر على `127.0.0.1:3001` **ولا يظهر**
على موقع الإنتاج — هذا هو دليل العزل، لا رمز الحالة وحده.

**nginx للموقع:** لا ملف له بعد. حين يُكتب: الشهادة أولاً (§٥ ثم §٤)، و`proxy_pass

2. منتجٌ بسعر ٤٠٠٠ وقطعتين ٧٠٠٠: السلة والمراجعة في الموقع ٧٠٠٠ لقطعتين (ولو

## ١٥. STEP 70 — «تحديث التطبيق»: نشر سياسة التحديث من اللوحة (بلا هجرة)

**فرقان لا يُخلطان:**

| | نشر إصدار على Google Play | نشر سياسة التحديث من اللوحة |
|---|---|---|
| أين | Google Play Console (رفع AAB، مراجعة Google، طرح) | اللوحة ← «تحديث التطبيق» ← «إرسال التحديث» |
| ماذا يغيّر | ما يُنزَّل من المتجر | ما يقوله الخادم للتطبيقات المثبَّتة: لا شيء / تنبيهٌ يُغلق / حجب |
| من يملكه | صاحب حساب Play Console | مسؤولٌ بصلاحية «الإعدادات» |

«إرسال التحديث» **لا يرفع APK/AAB ولا ينشر إصداراً على Google Play**. يُنشر الإصدار أولاً،
ثم تُنشر السياسة التي تشير إليه.

**خطوات المسؤول:**

1. انشر الإصدار على Google Play وانتظر توفّره للجميع.
2. انسخ رابط صفحة التطبيق: `https://play.google.com/store/apps/details?id=com.otakugalaxy.otaku_galaxy`.
3. «تحديث التطبيق»: الصق الرابط (يُعرض معرّف الحزمة؛ تحذيرٌ إن لم يكن الإنتاج)، أدخل
   «أحدث إصدار» (versionName كما في Play Console)، واختر النوع:
   - **اختياري** — النسخ الأقدم من أحدث إصدار ترى تنبيهاً يُغلق، مرّةً لكل إصدار. لا حجب.
   - **إجباري** — النسخ الأقدم من «أدنى إصدار مدعوم» تُحجب (شاشة بلا رجوع ولا «لاحقاً»،
     والخادم يردّ طلباتها بـ426)؛ وما بين الحدّ وأحدث إصدار ترى التنبيه الاختياري.
4. فعّل «تفعيل السياسة»، راجع المعاينة (نصّ التطبيق نفسه) و«النسخ المتأثّرة».
5. «إرسال التحديث» ← نافذة تأكيد (للإجباري تحذيرٌ صريح بالحدّ) ← «نعم، فعّل الحجب».
6. تحقّق من «ما تراه التطبيقات الآن» ورقم المراجعة وآخر تعديل.

**التراجع:** «إيقاف السياسة» في بطاقة الحالة ← تأكيد. يرسل `{ enabled: false, revision }`
وحده، فلا يُرفض بسبب أي حقلٍ آخر، ويرفع الحجب والتنبيه فوراً بلا إصدار ولا نشر خادم. أو
«استعادة هذه القيم» من «آخر التغييرات» (يملأ النموذج ولا يحفظ) ثم «إرسال التحديث».

**ما يحرسه الخادم:**

- الرابط صفحة **تطبيقنا** على Google Play وحدها (الحزمة بلا لاحقة أو `.staging`/`.dev`)؛
  يُحفظ بشكله القانوني. أي رابطٍ آخر أو مخطّط (`http`، `market:`، `javascript:`) 400.
- النسخ دلالية `1.2.3`؛ الحدّ ≤ أحدث إصدار (وإلا حُجبت كل نسخة بلا مخرج)؛ الاختياري يحتاج
  أحدث إصدار، والإجباري يحتاج الحدّ والرابط.
- «لا حجب عند الشكّ»: سياسةٌ برابطٍ غير صالح أو نوعٍ غير معروف (كُتبت خارج اللوحة) لا تحجب
  ولا تنبّه، واللوحة تعرض السبب.
- الحفظ معاملةٌ واحدة: قفل، فحص المراجعة (مسؤولٌ آخر حفظ قبلك ⇒ 409
  `APP_UPDATE_POLICY_CHANGED` وتُعاد القيم)، كتابة، وسجلّ `settings.app_version_updated` في
  `admin_audit_log` بلقطة السياسة. فشل السجلّ يُلغي الحفظ.
- `GET /api/catalog/app-version` عامّ للقراءة وحدها، `Cache-Control: no-store`. الخادم يخبّئه
  ثلاثين ثانية لكل عملية ويُبطله عند الحفظ: العملية التي حفظت فوراً، وغيرها خلال ≤٣٠ ث.

**قاعدة البيانات:** لا هجرة. مفاتيح `store_settings` جديدة: `app_update_mode`،
`app_latest_version`، `app_update_revision`. سياسةٌ حُفظت قبل STEP 70 (بلا نوع) تُقرأ
«إجبارية» كما كانت. **قبل النشر:** إن كان `app_update_url` المحفوظ ليس صفحة تطبيقنا على
Google Play فالسياسة تتوقّف عن الحجب حتى يُعاد حفظها برابطٍ صحيح — راجع الحالة في اللوحة بعد
النشر مباشرة.

**حدود معروفة:**

- تطبيقٌ لم يتّصل بالخادم بعد النشر لا يعرف بالسياسة؛ أوّل تشغيلٍ بلا شبكة لا يُحجب أبداً.
  فحصٌ فشل يُعاد بعد ١٥ ث ثم ٣٠ ث ثم ١ ثم ٢ ثم كل ٥ دقائق، وعند كل عودة من الخلفية، وعند أي
  ردّ 426. حجبٌ عُرف مرةً يصمد بلا شبكة وبعد إعادة التشغيل.
- لا يُحصى عدد الأجهزة لكل إصدار: «النسخ المتأثّرة» نطاقات إصدارات لا أعداد.
- لا إصدار iOS: الرابط صفحة Google Play وحدها.
- مقارنة النسخ على `versionName` (`1.2.3`)؛ رقم البناء (`+2`) لا يدخل فيها.


## ١٦. الهجرة 086 — النسخ الاحتياطية تُستعاد (`pg_dump` / `pg_restore`)

**العطل (بروفة هجرة الاختبار المسبق، 2026-10-25):** `pg_restore` لنسخةٍ احتياطية حقيقية
فشل في فهرسين فقط، `idx_products_search_ar_trgm` و`idx_products_search_ckb_trgm`:
`ERROR: function search_fold(text) does not exist`. الاستعادة تعمل بمسار بحثٍ فارغ،
ودالّتا مستند البحث (066) تستدعيان `search_fold` بلا اسم المخطّط. **يمسّ نسخ كل البيئات**
المأخوذة قبل 086: تُستعاد بلا فهرسَي البحث، أو تقف كلياً مع `--exit-on-error`.

| الهجرة | الأثر |
|---|---|
| `086_search_fold_schema_qualified` | الدالّتان بجسم 066 حرفياً، والفرق `public.search_fold(...)` وحده؛ تبقيان `IMMUTABLE PARALLEL SAFE` بلا `SET search_path` (وإلا لا تُدمجان ويخسر البحث فهرسه). تُنشئ الفهرسين إن غابا ثم `REINDEX` لهما. لا جدول ولا بيانات تتغيّر |

- **التطبيق:** بخطوة الهجرة المعتادة (§٢ أو §٣)، إضافية. `REINDEX` يحجب الكتابة على
  `products` لحظةً (الكتالوج صغير). لا ترتيب نشرٍ مع اللوحة أو التطبيق.
- **التراجع:** `scripts/rollback/086_search_fold_schema_qualified.down.sql` بالطريقة نفسها
  في §١٤، معاملةٌ واحدة. لا بيانات تضيع، لكنه **يعيد العطل**: كل نسخةٍ بعده تفشل في الاستعادة.
- **التحقّق بعد الهجرة (للقراءة فقط) — نسخةٌ تُستعاد في قاعدةٍ فارغة بلا أي خطأ:**

  ```bash
  ( cd /srv/otaku-galaxy-staging/backend          # الإنتاج: /srv/otaku-galaxy/backend و.env.prod
    DATABASE_URL="$(sed -n 's/^DATABASE_URL=//p' .env.staging | head -1)"
    PGOPTIONS='-c default_transaction_read_only=on' \
      psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -Atc "SELECT proname, prosrc ~ 'public\.search_fold\(' FROM pg_proc WHERE proname IN ('product_search_text_ar', 'product_search_text_ckb') ORDER BY 1" )
  ```

  السطران `product_search_text_ar|t` و`product_search_text_ckb|t`. ثم في بروفة الاستعادة
  التالية: `pg_restore --exit-on-error` لنسخةٍ جديدة يجب أن ينتهي برمز ٠.
- **[حرِج] استعادة نسخةٍ أقدم من 086** (أي نسخةٍ أُخذت قبل هذه الهجرة، على أي بيئة) — في
  **قاعدةٍ فارغة جديدة** لا فوق قاعدةٍ قائمة:
  1. `pg_restore` **بلا** `--exit-on-error`. المتوقَّع خطآن بالضبط، كلاهما
     `function search_fold(text) does not exist` عند `CREATE INDEX` للفهرسين أعلاه، وآخر
     الخرج `errors ignored on restore: 2`. أي خطأٍ آخر أو عددٍ آخر: توقّف وحقّق.
  2. خطوة الهجرة المعتادة على القاعدة المستعادة: تطبّق 086 (والنسخة تقف عند ما قبلها)،
     فتُصحَّح الدالّتان ويُنشأ الفهرسان.
  3. تحقّق كما أعلاه، و`\d products` يُظهر الفهرسين.

  جُرّب على نسخةٍ من 085: الخطآن ← 086 ← فهرسان صالحان ← نسخةٌ جديدة منها تُستعاد
  بـ`--exit-on-error` بلا خطأ. الدليل الدائم: `backend/tests/migration-086-dump-restore.test.ts`.
- **ما فُحص ولم يحتج تغييراً:** كل فهرسٍ وقيدٍ وقيمة افتراضية تعتمد على دالّةٍ من دوالّنا —
  الفهرسان وحدهما. `franchise_search_text` ليست في فهرس ولا تستدعي إلا دوالّ النظام؛
  `search_like_pattern` تستدعي `search_fold` وقت الاستعلام لا وقت الاستعادة.
